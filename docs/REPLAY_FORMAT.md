# Replay fixture v1

See the bundled sample `src/main/resources/replay/samples/weekly-buy-v1.json`. This is synthetic curated balance-delta data, not a raw Solana or provider capture. The synthetic zero wallet/signature is not the Decu identity.

The additive [real history capture](REAL_DATA_CAPTURE.md) saves raw transaction evidence and a separately versioned manifest. Those files are not v1 replay datasets and cannot be uploaded as such. Swap decoding and historical slot-aware market evidence must be verified before conversion; the capture does not alter this format, its checksum or simulation semantics.

The root has `schemaVersion` (exactly 1), `trackedWallet`, `transactions`, `observations`, and a SHA-256 `checksum`. Arrays are bounded to 10,000 records each. Times must be exact at microsecond precision, prices and liquidity must fit `numeric(78,38)`, `source` is at most 128 characters and observation `id`/`sourceEventId` at most 255; the loader rejects anything persistence would. Addresses must decode from base58 to 32 bytes, signatures to 64 bytes. Slots are nonnegative Longs. Monetary values and raw token deltas are decimal strings, never floating-point JSON numbers. Decimals are 0..255; accepted absolute raw amounts fit u64.

Transactions contain wallet, signature, instruction index, slot, optional UTC block time, base/quote mints, signed base/quote deltas, decimals, success/route/signer flags, source and commitment. The route flag reflects prior curation; this loader does not decode on-chain instructions or prove that a route is supported. The normalizer classifies opposing deltas as buy/sell, preserves raw amounts and provenance, and retains ignored outcomes. Repeated external identity is deduplicated; conflicting copies fail.

Observations contain ID, pair, observed slot, price slot (for age checks), UTC observed time, positive price, optional nonnegative quote liquidity, source, source event ID, commitment and quality (`LAST_TRADE`, `MIDPOINT`, `INVALID`). Missing liquidity means depth is unknown; the simulator cannot enforce an unprovided depth constraint. Quality and the source observation reference are retained on fills.

`DatasetFingerprint` is the canonical checksum specification: deduplicate identical records, sort transactions by slot/signature/instruction and observations by slot/ID, normalize decimals by stripping insignificant zeros, and hash each specified field as UTF-8 prefixed by its four-byte big-endian byte length. Times normalize through Instant. The algorithm includes schema version and tracked wallet. JSON whitespace, property order and duplicate delivery do not change the hash. Conflicting identities are rejected by the runner/catalog.

The configuration hash includes the strategy/version, numeric model parameters, scale/rounding, offsets, zero priority fee/price impact and confirmed signer-buy scope. The run ID combines engine version, dataset hash and configuration hash. The result checksum includes each intent's ordered fill/rejection, selected observation, position state and close economics. Increment the engine version if simulation semantics change.

In-memory replay is stateless and repeatable. Persisted replay writes source outcomes, observations, intents, orders/fills and positions together with run/configuration/input/report snapshots in one transaction. Dataset/configuration/engine identity has a database unique constraint. Concurrent duplicate writers converge on the original run; a conflicting result checksum fails. Process restart and repeated input create no duplicate lifecycle records. Stored datasets are identified by their checksum: registering identical content again, under any name, returns the existing dataset, and each persisted run also registers its dataset.

A missing exit observation in the bounded timeout window leaves the position open with an explicit reason; observations arriving after that window do not silently close it. Runs are immutable experiments, not a live checkpoint stream. Adding new observations changes dataset/run identity.

Persistence supports exact microsecond source times, observed decimals fitting `numeric(78,38)`, and modeled quote amounts and quantities fitting `numeric(38,12)` and modeled prices fitting `numeric(78,38)`. It retains original observation decimal scales and rejects finer source timestamps or unrepresentable values rather than allowing PostgreSQL to round. Wallet events and observations are bounded to 10,000 records per run; intents, orders, fills and positions to 30,000, three scenarios for each of up to 10,000 buys.
